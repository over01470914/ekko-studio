## R3 continuation (offline contract; not deployed)

The earlier CLI bearer instructions above describe the baseline only and are **superseded** by this continuation. The maintenance owner runs `node scripts/migrate-avatar-library-r3.mjs plan|apply|rollback` with the same scoped arguments (`--r2-catalog` for apply/rollback; apply additionally needs exact separately preapproved `--account-avatar-sha256` and `--codex-proxy-avatar-sha256`); no bearer is accepted. The process emits one JSON line `{kind:'mcp-request',id,profile:'default',method,path,body?}` per request, then waits for precisely one JSON line on stdin `{id,status,body}`. The authorized owner forwards it through the existing native `ekko_studio_api_request` with `profile=default`, `token` omitted, no user-provided Authorization header. Forward the *complete* JSON response and HTTP status, preserving opaque authentication inside the configured adapter. Do not forward text fragments or binary responses, log data URLs, persist credentials, or connect this bridge to an unapproved origin. Stop on non-2xx, malformed JSON, truncated/mismatched ID, or closed stdin. The `--origin` flag records the independently verified same-origin deployment target but the script itself never fetches that URL. The bridge/owner must bind its configured base URL to the supplied origin; otherwise defer. This is a protocol contract, not proof that the operator lifecycle guard permits live execution.

For byte-exact recovery, the protected `GET /api/hermes/profiles/:name/avatar/migration-snapshot/:hash` exports JSON `{mime,sha256,dataUrl}` only for the exact currently authorized image and the fixed 12-profile allowlist, with no-store caching, never in profile lists. Native MCP `response.text()` is **not** a binary backup. CLI independently decodes base64 and SHA-256-checks it against protected metadata before writing an exclusive 0600 fsynced backup, plus fsync of the recovery directory. The snapshot is private and must not be attached. Profile image restoration PUT uses exact backed-up bytes; cross-profile swaps and generated/custom uploads are refused by the approved r2 hash preflight. The historical `GET /api/studio/group-chat/rooms/muzvuy30vy9c4k/member-avatar-snapshots` exposes raw persisted `gc_room_members` rows (including removed/hidden rows, cap 256) to a native authorized room manager. CLI maps only current account's same-row avatar to `ip-012`, or a row whose `userId` equals an approved roster agent ID and whose old image hash matches that exact profile's r2 catalog to its mapped icon. Other accounts, unknown/custom/ambiguous rows remain unchanged and count as `unresolved`, requiring Naya decision rather than a fabricated zero count.
