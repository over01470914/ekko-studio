# Service Center 2.0.0 (SC02)

The host integration contract remains version 1. The optional compiled module and client both advertise version 2.0.0 and the same seven capabilities. The feature remains off unless `STUDIO_SERVICE_CENTER_ENABLED=1` is set at server startup. No production service inventory or credential is bundled.

## Wire format and behavior

The canonical export is `{schemaVersion:2,categories,nodes,services}`. The tracked [manifest schema](../../packages/server/src/modules/studio/extensions/service-center/manifest.schema.json) defines the structural fields and limits; runtime validation checks unique IDs/normalized names, category/node references, the default endpoint, URL safety and health settings. Category and node IDs use lowercase kebab-case and stay stable across rename; their display names and sort orders are editable. `categoryId`/`nodeId` can be null. Each service has 1–8 endpoints `{id,label,url,network,login}` and a valid `defaultEndpointId`. URL validation rejects userinfo, unsafe schemes, unknown/credential-bearing query keys and parameter-like fragments on every endpoint and the independent health URL.

The network enum is `local|lan|tailscale|public`; login is an editor declaration `unknown|required|none`. `local` refers to the deployment host, not the viewer's phone. Selecting another entrance updates only that page's link and network label. Backend checks remain per-service, require separate target approval, and never prove browser reachability. A reader sees enabled services and their own favorites but cannot mutate service, category, node or health approval. Editors use one catalog revision; category/node deletion requires explicit reassignment to an existing ID or null in one write. Grant administration stays super-admin only.

`PUT /api/studio/service-center/{services,categories,nodes}` upserts by ID with `expectedRevision`. `DELETE /api/studio/service-center/{services,categories,nodes}/{id}` uses the same revision; category/node deletes also require `reassignTo` (ID or explicit null). Import preview/confirm accepts v1 or v2, reports `sourceSchemaVersion`, typed `newIds`/`conflicts` and service references, and requires a `categories:id`, `nodes:id` or `services:id` keep/overwrite choice per conflicting ID. Import merges unmentioned records and validates references against the merged catalog. Export excludes favorites, editor grants, runtime health and health approvals. See [generated OpenAPI](../openapi.json) for the request schemas.

## Migration and rollback

Reads of persisted v1 data normalize to v2 without writing. The mapping preserves original service IDs, URL, network, description, enabled state, sort order, tags, health target/configuration and catalog revision; old category names become deterministic IDs, the lone URL becomes endpoint `primary`, and node remains null. New instances show two editable templates but do not persist them until a write. The first valid, authorized, non-stale catalog mutation writes `catalog-v1.backup.json` with the **exact original bytes**, file mode 0600, then replaces `catalog.json` with v2 under the module's serialized atomic file writer. A failed write rolls back the files; reloading v2 does not migrate twice. Keep the backup alongside a full private directory backup for any deployment-level rollback.

Do not start module 1.1.0 against a v2 catalog. For a rollback, stop the new module, restore the exact pre-migration `catalog.json` (and matched module data backup where necessary), then start the old binary. No automatic destructive downgrade or production migration is authorized by this source change. The opt-in [isolated preview procedure](README.md#focused-checks) exercises the new version with fixture accounts only.

The original r3 1.1.0 contract in [SPEC.md](SPEC.md) remains historical; it does not describe the v2 wire format. [SOURCES.md](SOURCES.md) records the concept-reference provenance and MIT attribution. No third-party source code, runtime dependency or new UI framework was added.
