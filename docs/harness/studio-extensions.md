# Studio extension contract v1

Studio remains the host. Extensions are compiled into the application, but **not** installed merely because their code exists. Service Center is the first opt-in extension. `STUDIO_SERVICE_CENTER_ENABLED=1` is the sole server registration switch; unset or any other value is off. Restart the server to change it. There is no runtime flag that bypasses authentication, no generic third-party module loader, and no public discovery.

## Registration and compatibility

- The server bootstrap supplies the explicit allowlist and a narrow host adapter to `modules/studio/extensions/registry.ts`. The Service Center implementation lives entirely under `modules/studio/extensions/service-center/`. It exposes contract version `1`, module version `1.1.0`, its own `/api/studio/service-center/*` router, and five named capabilities. Registration validates the ID, version, namespace and route methods **before** mounting, and a failed module's routes are disposed instead of half-installed. An off or failed module installs no route. `GET /api/studio/extensions` is mounted after the existing JWT middleware and returns `{contractVersion:1,extensions:[{id,version,apiBase,capabilities}]}` for installed modules only. Startup failure logs only the module ID and excludes it from discovery.
- The client bootstrap owns the authenticated request adapter, managed-user API, auth invalidation, locale and theme signals. It queries discovery before initial routing and after login, and matches an explicitly compiled allowlist with the **same version and all required capabilities**. It contributes a route and navigation to the existing sidebar, rail and mobile drawer only after success. Deep links are re-resolved after asynchronous registration. Authentication invalidation or server URL changes clear route, navigation, module store and late response state. Failure is local to the extension; core routes keep working. No module can register a route outside its designated path or an existing route name.
- Version is exact for v1, not a best-effort compatibility guess. A future incompatible contract needs an explicit adapter or a new version on both sides. Do not change existing grant rules, API payloads or file schema implicitly when changing registration metadata. `docs/openapi.json` includes authenticated discovery plus the module-owned schema and operations from `service-center/openapi.mjs`.
- `scripts/generate-openapi.mjs` collects extension contracts generically through `scripts/studio-extension-openapi.mjs`: it discovers `modules/studio/extensions/<id>/openapi.mjs` directories only, executes just a real non-symlinked file whose contract id matches its directory, and then requires every scanned extension route to sit inside `/api/studio/<id>/` with no path or operation-id collision and no host path or host schema mutation. A missing or escaping extension route fails the build instead of silently publishing a partial document. `scripts/check-studio-extension-boundary.mjs` is the executable dependency boundary: it asserts the upstream merge base, the allowed changed paths, the required upstream-equal router/settings sidebar/eleven locales/SafeFileStore files, the tracked module manifest/version, and that no module file imports the host `@/` or `modules/` trees other than the shared registry seam.

## Ownership and security

- The only server access to Studio config and account repository is `bootstrap/studio-extensions.ts`; the module receives `dataRoot`, an active actor resolver and an eligible-admin lookup. Requests pass existing JWT middleware first; the adapter re-reads the current account on **every** request. The module checks editor/super-admin grants for mutations and uses a private serialized atomic file store. Existing instance data remains under `HERMES_WEB_UI_HOME/service-center/{catalog.json,editors.json,health-approvals.json,favorites/<id>.json}`. No migrations or copies of existing data, no Hermes Agent home and no new credential storage.
- Client module code imports only its own files and the generic extension registry types. It uses host-provided authenticated request and managed-user functions; its translations are local and inherit the host locale without merging into host global dictionaries. It inherits host theme CSS variables. Navigation labels are rendered from its own locale messages, not a host translation key.
- Turning the switch off removes runtime API routes and UI discovery/navigation but does **not** delete any persisted records. Re-enable after rollback to resume the same catalog. Before upgrading, back up the module directory outside this repository. Never treat a backend health probe as proof that the user's browser can reach a service; explicit per-URL approval, DNS/IP filtering and bounded GET remain mandatory.

## Verification

`node scripts/check-studio-extension-boundary.mjs`, `npm run test -- tests/server/studio-extension-registry.test.ts tests/server/studio-extension-openapi.test.ts tests/server/studio-extension-boundary.test.ts tests/client/studio-extension-registry.test.ts`, `npm run test:e2e -- tests/e2e/service-center.spec.ts`, then `npm run harness:check` and `npm run build`. The module registry tests cover disabled, failed, version mismatch, auth gating, invalidation and late replies; the collector tests cover contract discovery, host-path/host-schema mutation, unresolved `$ref`s, auth downgrade, symlinked contracts and namespace escape. The opt-in isolated real-JWT preview procedure and screenshot outputs are documented in [Service Center README](../service-center/README.md). No production enablement is implied.
